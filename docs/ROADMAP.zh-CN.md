# FinancialBeancount 路线图

[简体中文](ROADMAP.zh-CN.md) | [English](ROADMAP.md)

本路线图记录不可遗漏的发布门禁。开发按可审计的小阶段推进，不代表应提前创建 Release。

## 当前交付主线

- 与账本内核一同打包的本地优先响应式 Web 应用。
- Windows、macOS、Linux 桌面控制器及可复现应用构建。
- 账本内核能够在应用内完全离线运行后，再进行 Android 原生打包。

## 发布门禁：无需卸载重装的更新

首次公开 Release 前必须完成并验证：用户账本及配置跨升级保留；迁移前备份及前向数据库迁移；版本化签名产物；用户主动检查、下载和安装；按系统与架构严格匹配；安装前展示版本、说明、大小及发布身份；下载后验证摘要和平台签名；使用原位安装或独立更新助手；网络失败不影响离线记账；失败时回滚二进制但不静默降级数据库；覆盖所有受支持历史版本；记录完全离线设备的手动更新方法。

## 已实现基础

- 用户主动触发的 GitHub Release 更新检查，以及可禁用或替换的 HTTPS 更新源。
- 平台/架构 ZIP、SHA-256 清单和 Ed25519 签名；内置公钥拒绝缺失、损坏或身份不匹配的更新。
- 有大小限制的流式下载、安全解压、路径穿越/符号链接/解压炸弹防护。
- 独立更新助手、健康检查、二进制备份和失败回滚。
- Schema 8、9 到当前 Schema 的事务迁移、校验备份、恢复入口和跨平台升级矩阵。
- 本地隐私门禁、禁止 API 缓存的浏览器边界，以及统一原始/标准交易 Schema 和可扩展账单适配器。
- 跨平台原生签名证据契约：固定发布者或指纹，并绑定准确安装包摘要。
- Windows MSI 的按用户安装、原位升级、卸载保留账本验收，以及 Authenticode、RFC 3161 时间戳和严格发布门禁。
- macOS 只读 DMG、拖放安装、替换升级数据保留，以及 Developer ID、强化运行时、公证、装订、Gatekeeper 和严格发布门禁代码。
- Android 无 localhost 的原生 JSON 桥接、应用私有统一 SQLite 初始化及静态资源白名单。

## 后续发布批次

当前验收与修复队列按以下顺序推进，避免被临时插入项覆盖：

### 已完成的升级节点

- Android 已通过应用内更新由 0.2.4 同签名覆盖安装到 0.2.5；ADB 已确认版本为 0.2.5，未卸载应用。
- 0.2.5 更新包不会自动恢复 V21 归档。V15、V21 是验收归档批次名称，不是数据库 Schema 版本；升级只保留并按需迁移原有数据库。升级后显示值变化须分别核查统计/余额算法变化，不得误判为自动导入了 V21。
- 0.2.6 已从提交 `4365e36f5215271e0bff490719a4bef269fa27f1` 完成主 CI、长期 Android 发布签名构建与公开 GitHub Release；公开附件仅包含签名 APK 和 SHA-256，不包含私人账单、余额、设备信息或本地验收归档。
- Android 已通过应用内更新由 0.2.5 同签名覆盖安装到 0.2.6；用户已在真机确认更新完成且原账本保留、账单可正常查看。0.2.6 APK 的 SHA-256 为 `1bfadc4226e6cc92bba7558e85fef43ab885c1fd2d871e761a030ddbf2597b16`。

### 当前有序队列

以下条目共同构成同一条长期发布路线，不是只保留前四项的新清单。“导入完备集 → 闪退 → 更新体验与加载/进度 → 全 UI”只是当前最近的执行窗口；统一账本回归、筛选、局域网入口、跨平台适配与发布、稳定正式版、正式版后皮肤系统仍按本文件顺序接续。后续临时插入的问题必须补入此处并注明优先级或阻塞关系，不得只留在会话上下文中。

1. 完成五平台账单的单文件、多文件、文件夹导入完备集验收，再恢复最新完整账本；覆盖工商银行两种正确 PDF 版式及重庆农村商业银行适配器。重点验证错误文件不会造成部分写入、重复导入保持幂等、进度和结果按文件可见。
2. 复现并修复页面切换及页面内按钮操作时的偶发闪退，采集 Android 崩溃日志与稳定触发步骤，补充页面和按钮稳定性回归测试。
3. 完成更新交互的剩余体验修复：严格区分“连接 GitHub”“获取校验信息”“连接下载”“实际下载百分比”“文件校验”和“交给系统安装器”；窄屏下使用独立进度文字和进度条；网络超时显示中文原因、VPN 建议与重试入口，不得残留裸 `timeout`。0.2.5 → 0.2.6 的真实自动更新与同签名数据保留已经通过，后续版本继续回归该链路。
4. 优化各页面数据加载耗时，并为导入、导出提供明确进度和操作锁定，防止重复或干扰操作；错误状态必须使用友好说明、重试动作，不直接展示底层异常字符串。
5. 继续核对统一账本：银行余额链与微信/支付宝独立链、跨平台去重、银行卡账单滞后补算、每笔余额锚点，以及“全部收支差额与账户余额”的解释性提示。不得用伪造跨平台平账替代证据链；已经闭合的五平台区间应固化为自动回归基线。
6. 继续已临时搁置的全 UI 页面重构：覆盖概览、交易、审核、数据及其全部子页面，而非只处理四个顶层入口；优先使用成熟的原生组件和模式，保持统一设计系统，并按 Android、Windows、macOS、Linux 和 Web 分别适配，避免 WebView 式生搬硬套。
7. 完成概览周期卡可点击下钻，以及来源、账户、日期、方向、金额、分类、商户、备注和待处理状态等组合筛选与状态保持；“全部来源”默认代表全部已选。
8. 在不影响本地优先模式的前提下，为 Android、Windows、macOS、Linux 和 Web 客户端补充可选的局域网使用入口：发现或手动填写主机、令牌认证、连接状态、数据库更新/同步边界、断线回退和显式停止服务；默认不开启、不常驻、不直接共享 SQLite，完成后验证服务器与端口可彻底关闭。此项在正式版前完成，但优先级低于本地功能完备与账本正确性。
9. 进入跨平台 UI 一致化和多平台发布验收，最后发布首个稳定正式版本；皮肤系统仍排在正式版之后。

### 公开发布隐私门禁

- 公共 GitHub Release 只能包含通用版本号、面向用户的功能/修复说明、公开安装包、校验值和签名，不得包含真实账单、余额、账户、手机号、设备标识、本机路径、验收归档或可识别个人的内部测试细节。
- 发布前检查源码追踪文件、安装包内容、Release 正文和附件；内部验收报告与私人数据只保留在本地忽略目录，不上传 GitHub。

- 统一 GitHub Release：同一版本集中附加 Android、Windows、macOS、Linux、网站静态包（适用时）、校验与签名文件，并保留 GitHub 自动生成的源代码归档；所有平台使用一致版本号。

- 配置实际 Windows 和 Apple 发布者凭据，并在干净 Runner 上完成正向验证。
- 使用实际发布者 OpenPGP 密钥完成 Linux AppImage 签名正向验证；AppImage 构建、替换升级、卸载数据保留和严格门禁代码已完成。
- 每次正式发布后，将该版本加入持续升级兼容矩阵。
- 建立 Kotlin/Gradle Android 工程、Storage Access Framework 批量导入与 WebView 安全边界，再接入 APK/AAB 签名和升级验收。

## 正式版后的外观扩展

首个正式版稳定发布后再加入轻量皮肤系统，不阻塞当前功能、数据准确性和更新链路验收：

- 保留当前界面作为默认皮肤，并设计一个不依赖第三方角色素材的默认软件图标。
- “希儿芙乐艾－死生之律者”“希儿芙乐艾－彼岸双生”“希儿芙乐艾－愈生佑翎”三个可选皮肤，各自包含配套图标，并把显示名称切换为“希芙の账单”。
- 皮肤只能改变颜色、背景、图标和显示名称，不得改变统一账本 Schema、业务规则或用户数据目录。
- 图标与显示名称必须覆盖打包层，而不只是在程序界面内替换：包括 Android 启动器图标与应用名、桌面端可执行文件/安装包/快捷方式图标与名称，以及各平台包元数据。切换方案需明确哪些变更可运行时完成、哪些需要生成对应的安装包变体，并保持同一应用身份与可原位升级能力。
- 角色图片、名称和衍生图标在进入公开 Release 前必须由实际发布者确认许可范围；仓库不得直接收录来源或授权不明的官方素材。

## 正式版前补充项

- 已完成：“关于”页面展示软件标记、作者 GitHub、项目 GitHub 与上游出处和许可证。
- 已完成：“删除全部数据”采用明确说明影响范围的二次确认，并在删除完成后回到空账本状态；不会删除应用安装包。
- 完整账本验收必须审计基金/理财、退款、跨账户转账和疑似重复记录；仅在“全部账单 + 全部来源”口径下比较收支差额与账户余额，不一致时须提示账单开始前未计入余额或账单可能不完整。
